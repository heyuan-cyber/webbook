## 3. 还没解决的五件事

| # | 问题 | 证据 |
|---|---|---|
| **1** | **桌面没有任何可见的「去处」** | 5 个目的地（个人主页 / 社区 / 圈子 / 后台 / 皮肤）全在头像菜单；桌面没有当前页高亮。手机底栏反而有 4 个 → **桌面导航比手机弱** |
| **2** | **两套导航的目的地集合不同** | 账号菜单 6 项 vs 底栏 4 项，交集只有「社区」。手机**没有圈子的常驻入口**，桌面**没有「笔记」入口** |
| **3** | **首屏仍是死灰色** | `/app` 正中央两行灰字，1600×1000 里 90% 空白 |
| **4** | **`/blog` 双层头部** | `BlogHubPage.tsx:160` 渲染 `ShellTopBar`，`:174` 又渲染 `blog-header`；登录 / 皮肤各出现两次；内容仍挤在 570px，右侧 40% 空 |
| **5** | **移动端两个确定的缺陷** | 底栏一行需要约 480px → **≤470px 时第 4 项「我的」在屏外**；首屏说明文字横向溢出被裁 |

### 第 5 条的实测数据

同一页面在四个宽度下 headless Chrome 实拍（`_now/_nav-*.png`）：

```
宽度    底栏可见项
500px   笔记 任务 社区 我的   ← 4 项都在
460px   笔记 任务 社区 [我]   ← 第 4 项只露一个边
430px   笔记 任务 社区 [我]   ← 同上
390px   笔记 任务 社区        ← 第 4 项完全在屏外
```

问题区间确认在 **≤470px**，覆盖 iPhone 全系（390–430px）。这一条在 390 / 430 / 460 三个宽度下都可复现。

## 4. 核心主张：一份 nav 数据，两种布局

现在的问题不是「顶栏不好看」，是**桌面和手机各自维护了一份导航**。解法不是再加一层导航，而是把去处抽成一份数据：

```ts
const PLACES = [
  { key: 'notes',   label: '笔记', icon: 'book',  to: '/app' },
  { key: 'blog',    label: '博客', icon: 'globe', to: '/blog' },
  { key: 'circles', label: '圈子', icon: 'users', to: '/app/circles' },
  { key: 'me',      label: '我',   icon: 'user',  to: '/blog/u/:me' },
];
// 桌面：<nav class="nav">   横向排（≤1080px 只留图标）
// 手机：<nav class="m-nav">  底栏竖排（即现在的 MobileNav）
// 账号菜单：只剩 后台 / 皮肤 / 退出
```

这样「手机上有的，桌面也一定有」不再靠人记。

## 7. 顺带发现（不属于设计范围）

1. **圈子的游客守卫** —— 游客访问 `/app/circles` 被重定向到登录页（截图与 `/login` 逐字节相同）。但 `CircleListPage` 已经引入了 `ShellTopBar`：代码准备了外壳，守卫没让它渲染。若公开圈子本来可匿名读，放开比一堵墙好。
2. **侧栏玻璃没有东西可透** —— `.sidebar` 用 `--glass-bg`(62%)、`.topbar` 用 `--glass-bg-strong`(82%)，但底下是同色背景，结果只是**降低了对比度而没有制造深度**。要么改实色，要么给背景加真实内容。
3. **个人主页 feed 返回空** —— 上一轮已记录：`/api/public/users/:id/feed` 对一位有公开文章的作者返回 `{"posts":[]}`，且 `ownerEmail` 等于 userId。建议单独开 issue。
