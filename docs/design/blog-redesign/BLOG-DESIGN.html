这版博客改了什么（先看结论）

  • 容器从 920px 放到 1200px —— 实测线上 .blog-header-inner 与 .blog-main 都是 max-width:920px， 但内容只用到其中 ~560px（.blog-list 864px 里两列卡），1600px 屏上右侧三成是空的。这是"页面看着空"的根因。
  • 页头从"一列堆叠"改成整宽 masthead —— 标题、导航、tab、检索按品牌区/操作区/tab 条三层排开，不再挤在同一列。
  • 补上"重点"层级 —— 现在所有卡片一样大、一样空。改为「1 张头条大卡 + 等高网格」， 头条用编辑式排版（kicker + 大标题 + 摘要）撑起首屏，无封面也不塌。
  • 卡片把数据用起来 —— PublicFeedItem 里本来就有 summary / cover / category / updatedAt， 但界面只显示了标题 + 作者 + 日期 + 「阅读 →」。现在补摘要两行、分类 chip、封面可选、底部对齐。
  • 加一条时间线"更新流" —— 广场下方按更新时间列全部公开文，日期用等宽字体成列，扫读快。
  • 文章页重排 —— 标题区（分类/kicker → 大标题 → 摘要引文 → 署名）与正文分开；正文 18px/1.85/68ch； 右栏常驻目录随阅读高亮；代码块带语言标签；图片有 figcaption。
  • 文末补齐 —— 作者卡 + 相关文章 + 评论（原来文章读完就断了）。
  • 移动端 —— 博主条改横滑（现在换行 flex 会把内容顶出屏幕），卡片单列，目录折成可展开条。
  • 全部走 token —— 换皮肤（墨金/纸墨/蓝图）博客一起变，不会出现"白字压白纸"。

战损贴花使用指南

贴花是战损表现里最便宜的手段，但层数与排序决定了它是省事还是掉帧。这篇给出三档质量预设、实测 drawcall，以及移动端该关掉什么。

1 1060707057 2026-09-10 约 6 分钟 2 480 字 public

贴花（decal）是战损表现里最便宜的手段：一张带透明通道的贴图投影到受击面，不需要改模型拓扑。但它有两个容易被低估的成本 —— 层数和排序。

三档质量预设

按目标机型给出三档，每档限制最大同时存在的贴花数：

textlow    : 24 个 · 512²  · 不参与排序
medium : 64 个 · 1024² · 按距离排序
high   : 128 个 · 2048² · 按距离 + 法线夹角
先测 drawcall，再调贴图尺寸。多数时候瓶颈在提交次数而不是带宽。

常见坑

  • 贴花法线与受击面夹角大于 60° 时会出现拉伸，需要在 shader 里做投影裁剪。
  • 同一帧内叠加超过 8 层会触发 overdraw 警告，建议按材质分组合批。
  • 透明通道的边缘要用 alphaTest 而不是混合，否则排序会闪。

移动端取舍

移动端不要开 high 档的按法线夹角排序，实测 GPU 时间增加 40%，而画面差异在 6 寸屏上几乎看不出来。

如果只能记一句话：把层数上限当成帧预算来管，而不是当成美术参数来调。

设计说明与落地要点

一、为什么是"编辑式"而不是"卡片瀑布"

  • WebBook 的博客本质是技术文档的公开面，不是内容农场。技术读者要的是"这篇讲什么、多长、谁写的、什么时候"，而不是图片墙。
  • 而且你现在的数据里大多数文章没有封面图（cover 可选）。所以设计必须在无图时依然成立 —— 头条用排版撑场，卡片用摘要撑场，图片只在有时才放大。
  • 因此没有做瀑布流/大图卡片墙：那会让无图文章变成一堆空洞。

二、信息层级（三层，不再"所有卡片一样重"）

  • 头条（1 张，整宽两栏）：kicker + 大标题 + 完整摘要 + 元信息 + 右栏统计/封面。
  • 最新文章（等高网格，自适应 2–3 列）：分类 chip + 标题 + 两行摘要 + 底栏元信息。
  • 更新流（条目列表）：日期成列 + 标题 + 一行摘要 + 作者。用于"我就要找那篇"的场景。

三、效果清单（都做了降级）

  • 卡片 hover：边框转强调色 + 背景提亮一级 + translateY(-2px)；用 --hover-raise，纸墨皮肤下减为 -1px（纸上位移感更弱）。
  • 封面 zoom：仅在 @media (hover:hover) 下对封面做 scale(1.04)，避免触屏误触。
  • 滚动揭示：沿用现有 Reveal，但把 stagger 限制在首屏 4 个元素内，且 prefers-reduced-motion 下直接静态。
  • 阅读进度：顶部 2px 条 + 目录底部百分比，均只过渡 width。
  • 所有动效只动 border-color / background / transform / opacity，不触发布局重排。

四、需要你拍板的三件事

  • 「更新流」要不要？ 它让广场变长，但扫读效率最高。若你觉得重复，可以只保留"头条 + 网格"。
  • 头条固定取"最新一篇"还是支持手动置顶？ 手动置顶需要在站点配置里加字段（SiteConfig）。
  • 要不要显示阅读时长/字数？ 需要按字数估算（约 400 字/分钟），会给每张卡片一次正文长度读取（若走 feed 接口拿不到正文，可先用摘要字数近似）。

五、落地顺序建议

  • P0 容器 920→1200 + masthead 重排 + 卡片等高/页脚贴底（纯 CSS，改动最小，收益最大）。
  • P1 卡片补摘要/分类/时长（用已有 PublicFeedItem 字段，无需改后端）。
  • P2 头条模块（新增标记，纯前端）。
  • P3 文章页重排（标题区 / 正文规格 / 目录 / 文末三段）。
  • P4 个人主页 hero + 作品横滑。
  • P5 更新流 + 检索/分类筛选（需要前端过滤，数据量小时够用）。
