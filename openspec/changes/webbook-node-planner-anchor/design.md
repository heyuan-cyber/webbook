## Context

见 `proposal.md` — Why。设计只需要三个现实前提：

**1. 数据模型已经够用，不需要迁移。** `PlanNode.anchorNodeId?: string` 本来就是可选字段，`selectVisibleTasks` / `collectSubtreeNodeIds` 的聚合逻辑在 `packages/shared/src/plan.ts` 里已实现且被断言覆盖（`scripts/assert-plan.mjs` 的 84 项）。所以这次**不改数据、不改 Worker、不改 API**——只补前端缺失的赋值与入口。

**2. `visibleTasksForScope` 的可见性规则是"锚点落在该节点子树内"**（design D3）。这条规则本身正确，问题在于**没有任何任务被赋过锚点**，于是它一直在对空集求并。修复必须落在"创建路径"上，而不是放宽可见性规则。

**3. 组件树里 scope 的节点 id 目前只到 `PlanSurface` 就停了。** `openPlanner` 把 scope 存进 store，但渲染 `<PlanTaskTree>` 时只传了 `tasks` / `scopeKey` / `mobile`，`scope.nodeId` 没有往下走。

## Goals / Non-Goals

**Goals:**

- 让"在侧边栏创建的任务属于该笔记/栏目"成为**结构上不可能违反**的事，而不是依赖用户记得去绑定。
- 消除锚点的设置/解除不对称，让归属**可见且可改**。
- 把"每个笔记/栏目是一个任务筐"这个心智模型固化进 spec，使后来者重构 UI 时不会误删锚点入口。

**Non-Goals:**

- 不放宽"父栏目聚合到最深后代"的可见性规则（那是正确的，且已被 spec 与断言固定）。
- 不做任务在筐之间的批量迁移 UI（用户已确认历史任务自行处理）。
- 不改任务树的嵌套语义——任务嵌套服务"这件事怎么拆"，锚点服务"这件事属于谁"，二者正交，本次只把这一点写清楚。
- 不为锚点引入多值（一个任务只属于一个筐）。多归属会让父栏目递归收集出现重复计数，且与统计口径 D7 冲突。

## Decisions

### D1. 锚点在创建时赋值，而不是在渲染时推断

```
PlanSurface                         PlanTaskTree                       TaskCreateForm
    │                                    │                                   │
    │ scope.kind === 'node'              │                                   │
    │ ? scope.nodeId : undefined         │                                   │
    ├────── scopeNodeId ────────────────▶│                                   │
    │                                    ├──── scopeNodeId ─────────────────▶│
    │                                    │                                   │
    │                                    │                    draft.anchorNodeId
    │                                    │◀──────────────────────────────────┘
    │                                    │
    │                        store.addTask(parentTaskId, draft)
    │                        ⇒ task.anchorNodeId = draft.anchorNodeId
```

**为什么不在渲染时按 scope 推断可见性？** 那等于放弃锚点模型，退回"任务属于你正在看的那个节点"的隐式归属。代价是：同一个任务在不同视图里归属不同，父栏目递归收集失去意义（没有稳定的"属于"可收集），且任务在筐之间移动会变成隐式的。锚点必须是**存下来的事实**，不是**算出来的视图**。

**替代方案**：把 `anchorNodeId` 从可选改为必填（`string`）。否决——历史数据里有 2 条无锚任务，且全局中心的收件箱本身就需要"暂无归属"这个状态。

### D2. 子任务继承父任务的锚点

在节点 scope 内创建子任务时，`anchorNodeId` 取自**父任务**当前的值，而不是取自 scope。

**理由**：spec 的 `Anchor is independent of nesting` 允许子任务自带锚点或继承。但若允许"不带锚点"，就会出现父任务锚在 A、子任务无锚的组合——**父任务在 A 的规划里可见，子任务不可见，树缺一块**。继承父任务的筐可以完全避免这个状态，且不需要用户理解锚点概念。

**副作用（可接受）**：从父任务拖动一个子任务到根级，它仍留在原筐里。这正确——拖动改变的是任务树结构，不是归属（D4）。

### D3. 收件箱就是全局任务中心，不再需要独立的"收集箱"节点

用户确认的模型是"在侧边栏创建 → 归到该节点"。那么"未选节点"这个状态只应在一个地方产生：**全局任务中心**。它已经有「未归类」筛选与 `PlanScopePicker`，天然就是收件箱。

**因此不引入新的 `__inbox__` 哨兵节点 id。** 无锚（`anchorNodeId === undefined`）本身就是收件箱的表示，与现有 `collectUnclassifiedTasks` 语义一致，零改动。

**替代方案**：给每个用户预置一个"收集箱"栏目节点。否决——那会污染用户的笔记树，且让"栏目"这个概念承担两种语义（真实栏目 vs 系统筐）。

### D4. 拖动只改任务树，不改锚点

任务在筐内的拖动（排序 / 改层级）不触碰 `anchorNodeId`。

**理由**：任务嵌套回答"这件事怎么拆"（子步骤、依赖），锚点回答"这件事属于谁"。把两者绑定会导致：想把一个子步骤提升为同级，就把它挪出了所属栏目——这在语义上是错的，也会让父栏目聚合结果随拖动意外变化。

**实现上无需额外代码**：现有 `moveTask` 只操作 `children` 数组，不碰 `anchorNodeId`。这条要求的作用是**防止将来有人把它耦合起来**，所以写进 spec 并加断言。

### D5. 详情面板的锚点入口在所有 scope 下都可用

现在的不对称是：`onRequestAnchor={tree ? ... : undefined}` 而「解除绑定」无条件渲染。修法是**统一为都可用**，而不是"在节点 scope 下隐藏解除按钮"。

**理由**：用户明确要"归类可改"。限定只能在全局中心改，会让"我想把这条任务挪到另一个栏目"变成需要跨视图操作的绕路。`PlanScopePicker` 已经存在且接受任意 `TreeNode[]`，`PlanSurface` 在任意 scope 下都能拿到 `tree.roots`，传下去即可。

## Risks / Trade-offs

- **拖动一个已锚定的任务到另一个筐的规划里，它不会改归属** → 这是 D4 的刻意结果，但用户可能期望"拖过去就归它"。缓解：任务行始终显示当前筐名（spec 要求），归属变化只能通过显式改锚点发生，不会静默。若将来需要，可加"拖到别的筐时提示是否同时改归属"——不在本次范围。
- **强制锚定让节点 scope 无法创建"临时无主任务"** → 用户已确认接受；全局中心是明确出口。风险是新用户不知道这个出口。缓解：空状态文案应指出全局有未归类任务（本可在后续 change 做，本次不强制）。
- **子任务继承父任务锚点，可能让用户无法在筐 A 里为筐 B 建子任务** → 属真实取舍。若确实需要跨筐子任务，用户可先创建后改锚点（D5 提供了入口）。记录为已知限制。
- **历史无锚任务与新规则并存** → 用户自行绑定。`collectUnclassifiedTasks` 与「未归类」筛选继续存在正是为此，不视为技术债。

## Migration Plan

**部署**：纯前端改动，与 Worker 无关。前端发布即可，无顺序约束，无数据迁移。

**回滚**：改动集中在两个组件文件，回滚即恢复"创建不带锚点"的旧行为；已带锚点的数据在新旧版本下都能正确渲染（`anchorNodeId` 一直是可选字段），因此回滚不会损坏数据。

**验证**：
- 在节点 scope 创建任务 → 该任务的 `anchorNodeId` 等于该节点 id，且立刻出现在同一视图。
- 在节点 scope 创建子任务 → 子任务 `anchorNodeId` 与父任务一致。
- 在全局中心不选节点创建 → 出现在「未归类」。
- 改锚点 / 清除锚点 → 任务在相应视图中移入移出。
- 拖动任务 → `anchorNodeId` 不变（断言覆盖）。
